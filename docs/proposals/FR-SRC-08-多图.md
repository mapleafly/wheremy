## 1. 一句话价值

用户不必再为了"这件东西想拍两张"而**建档两条**，也不需要为了拍特写而**把原来那张换掉**。

## 2. 用户场景

- 前置：机器里有几件物品（每件一张照片）、两层位置；AI 已配或未配都行。
- 步骤：1) 打开一件已存好的物品 → 2) 想再拍一张吊牌特写 → 3) 拍完挂到**同一条记录**上 → 4) 详情页里左右翻看两张，墙上那格仍用第一张当封面。
- 现状哪里不够用：
  - **没有办法给已有物品再加照片**——相机/选图那条路只会新建一条记录（`newDraft`）；
  - 想把特写挂上去，只能删掉原照片重拍（原图丢）；
  - 或者建第二条记录，于是同一件东西在墙上占两格、搜索里出现两次、到期提醒可能说两遍（`DECISIONS.md` D13 就是为"多角度被当多件"留的记录）。

## 3. 成功判据（可测）

| # | 判据 | 怎么测（命令 / 界面动作） |
|---|---|---|
| 1 | 一件物品能有 **N 张**照片，且**按加入顺序**返回 | 单测：`photosOf(item)` 返回 N 行、`sortOrder` 递增 |
| 2 | 墙上的封面 = **第一张** | 单测 + 真机看一眼：`thumbPathOf` 等于第一行的 thumb |
| 3 | 删掉物品时，**只有没人再引用的照片文件**被删 | 单测：两张物品共享一张照片时删其一，文件仍在；删其二，文件才没 |
| 4 | 删掉**单张**照片后，同一件物品的其它照片不受影响 | 单测：3 张删第 2 张 → 剩 2 张、顺序补位 |
| 5 | 备份往返后照片张数与顺序一致 | 单测：导出 → 导入 → 张数与 `sortOrder` 完全相同（含共享同一张文件的两件物品，包里仍只有一份文件） |
| 6 | 真机：给一件已存的物品再加一张，墙上与详情页都对 | 真机动作（`REBUILD.md` §6 风格） |

## 4. 与现有 FR 的关系

- 关系：**扩展** `FR-SRC-01`（拍照/选图录入）与 `FR-FND-*` 的详情页；不改 `FR-BAK-01/02` 的语义。
- `PRD.md` §7 守门测试索引：给 `FR-SRC-08` 加一行，指向新增的 `ItemPhotoMultiTest`（数据层）与 `DetailScreen` 的 Compose 测试。
- 与 `DECISIONS.md` D13 的关系：D13 说的是"**一张照片里**同一件的多个角度当多件处理"（AI 侧，保持不动）；
  本提案管的是"**一件记录挂多张照片**"。两者不冲突，但要在 `RULES.md` 里写清"封面 = 第一张"。

## 5. 触发条件与代价（必填）

| 项 | 内容 |
|---|---|
| 触发条件 | 用户开始要求"正面 + 吊牌特写"两张图挂同一条记录（`PRD.md` 原文） |
| 代价 | **中**（比原估的"大"低一档，见下"实测底子"） |
| 现在为什么不做 | 触发条件尚未出现；且不做也能凑合（建两条记录 / 换掉那张照片） |

**实测底子（这是本提案最有价值的部分：原估"大"是没核实的估计）**：

| 原估要动的 | 实测结论 |
|---|---|
| 备份去重 | ✅ **已经在做**：`BackupRepository.putOnce` 按相对路径去重；`data.json` 是四表行序列化，多行 `item_photo` 天然带得出去 |
| 数据模型 | ✅ **本来就是多行**：`item_photo` 主键是行 id、带 `sortOrder` 与 `(ownerType, ownerId)` 索引 → **不动 schema、没有 Migration** |
| 读照片 | ✅ `photosOf(itemId): List<ItemPhotoEntity>` 已经有；**详情页已经在渲染列表**（`DetailViewModel.photoPaths: List<String>` + `DetailScreen` 的 `items(photoPaths)`） |
| 多图 UI | ⬜ 缺"给已有物品加照片/删某一张"的入口与规则 |
| 引用计数 | ⬜ **确有坑**：`photoDeletionOf` 与 `delete` 用 `firstOrNull()` 只看封面那一张（`ItemRepository.kt:485`、`:504`）——多图之后会导致**该删的文件没删（泄漏）或删了别人还在用的文件**。这两处必须改成"遍历所有行、按路径合并引用计数" |

**真实工作量**：数据层 2 处（约 40 行 + 单测）、仓库新增 `addPhotoToItem` / `removePhoto`（约 40 行）、
UI 2–3 处（详情页加/删、录入页支持连拍）、测试约 10–15 例、文档 5 份（`PRD`/`RULES`/`UI`/`TESTING`/`CHANGELOG`）。
**不碰**：schema、备份格式、权限、签名。

## 5.1 备选项与建议

| 选项 | 做什么 | 代价 | 什么时候选 |
|---|---|---|---|
| **A（完整做）** | 加照片 / 删单张 / 封面=第一张 / 引用计数改对 / 测试与文档 | 中（见上） | **建议**：真需要"一件多图"时 |
| **B（最小做）** | 只做"再加一张"，不做删单张 | 中偏小 | 只想要"多拍几张"，且能接受删照片要整条删 |
| **C（不做）** | 维持 ⬜；继续用"建两条记录"或"换照片"凑合 | 0 | 现在根本没有这个诉求时 |

**我的建议：如果这个诉求已经出现，就选 A**——理由是底子比文档里写的厚（表、列表渲染、备份去重三样都已就位），
真正要写的是"加/删照片"这条竖切 + 修两处只看封面的引用计数；**它是加法的、没有迁移风险**。
如果诉求还没出现，**C 也完全合理**：这件事晚做不会变贵（不像备份格式那样动一次要重演练一次）。
