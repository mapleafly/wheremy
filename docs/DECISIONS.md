# Wheremy 架构决策记录（DECISIONS / ADR）

**这份文档回答**："**为什么这么定**"。`PRD.md` 说要什么，`ARCHITECTURE.md` 说现在长什么样，本文说当初为什么这么定、什么条件下该重新讨论。

**它记录的是决定与理由，不是现状**：决策与现状不一致时，**以 `ARCHITECTURE.md`（as-built）为准**，并在该条 ADR 的"后果"里照实标注 ⚠️。

**口径**：代码基线 commit `cf73f5b`（2026-10-06）。本文与 `PRD.md` §6 的关系是：**§6 是索引表，本文是权威详表**；两处必须一致，不一致时改 §6。理由一律照抄现有文档的措辞（`PRD.md` §6、`ARCHITECTURE.md` §15、`RULES.md` §15/§16、`REBUILD.md` §2 或源码注释），这里不重新论证。

## 1. 这份文档是什么

**本文是一份架构决策记录（ADR）**。每一条回答四个问题：**当时面对什么**、**决定了什么**、**代价是什么**、**什么条件下该重新讨论**。

| 文档 | 回答 | 口径 |
|---|---|---|
| `PRD.md` | **要什么**（每条带 `✅/🟡/⬜/⛔` 状态、触发条件与代价） | 目标态 |
| `ARCHITECTURE.md` | **现在长什么样**（分层、类、调用顺序、跨层不变量） | as-built |
| 本文 | **为什么这么定、什么时候该重看** | 决策记录 |

四条使用规则：

1. **决定与现状不一致时以 `ARCHITECTURE.md` 为准**，本文只负责解释"当初为什么这么定"以及"后来有没有被改掉"（改掉的那条在 §5 留痕）。
2. **`PRD.md` §6 的 `⛔D1–D14` 是索引表，本文是它们的权威详表**。编号映射写进每条标题（`ADR-nn ← PRD ⛔D…`），一句话决策与理由必须与 §6 一致。
3. **本文不回答**"要做什么"（→`PRD.md`）、"规则到底怎么算"（→`RULES.md`）、"屏幕怎么摆"（→`UI.md`）、"先做哪一步"（→`REBUILD.md`）。
4. **状态标记只认四种**（`README.md` §6）：`✅ 已落地` / `🟡 部分落地` / `⬜ 待做` / `⛔ 已否决`。本文用到 `⛔` 时指的是**那件事被否决**；一条 ADR 自己的**状态**是另一回事，见 §2.2。

## 2. 怎么用：ADR 流程

### 2.1 什么时候必须写一条 ADR

落进下面六类里的任何一类，就**先写 ADR 再动手**（`README.md` §5 的变更通道里，"改 schema / 备份格式"那一栏本来就要求用 `templates/adr.md`）：

| # | 触发 | 为什么必须留痕 |
|---|---|---|
| 1 | **推翻任何 `⛔`**（`PRD.md` §6 的 D1–D14） | 否决理由留着就是为了"避免下一次又讨论一遍"；要推翻，得先在 `PRD.md` §6 里改掉并写明新理由 |
| 2 | **改 `REBUILD.md` §2 的不可变项**（13 行） | 那一节的标题就是判据："**改了就不算这个 app**"；每条都写清了定义在哪、为什么不许动 |
| 3 | **改备份包格式或 Room schema** | 旧包必须还能导入；验收期间 schema 冻结（`WheremyDatabase.kt` 的 `fallbackToDestructiveMigration(true)`，见 `RULES.md` §15 W2） |
| 4 | **换技术栈 / 组件库 / 相机、图片加载这类地基** | 逐字文案与界面测试是按当前栈写的；信息架构还要照 `UI.md` §12 复现 |
| 5 | **改一条 🔒 规则**（`RULES.md`） | 🔒 的定义就是"改了就有一条界面文案或一条测试变成假话" |
| 6 | **引入新依赖大类**（DI 框架、ORM、UI 框架、大模型 SDK…） | `PRD.md` NFR-07：新依赖要回答"标准库/已有依赖做不了吗" |
| 7 | **自造一处新机制**（不引库、自己写一套） | 用户 2026-10-07 拍板的准则（`ADR-25`）：自造必须写清"找过谁、为什么不用、代价是什么"，并给复核触发条件——否则下一个人无法判断这是取舍还是偷懒 |

**不需要写 ADR 的**：改一处笔误、补一条测试、把现状描述改准（那属于 `ARCHITECTURE.md` / `RULES.md` 的职责）、以及任何"不改变已定行为"的重构。

### 2.2 状态机与编号规则

```
提议 ──► 接受
     └─► 否决
接受 ──► 被 ADR-N 替代        （有人推翻它，并且新写了一条）
接受 ──► 废弃                 （问题本身没了：功能删除、前提消失）
```

- **状态只有这五种**：`提议` / `接受` / `否决` / `被 ADR-N 替代` / `废弃`。
- **编号 `ADR-01` … 只增不改号**：新决策一律往末尾加，**不许**把已发布的号挪给别的事，也不许在中间插号（插入会让所有交叉引用集体挪位，同 `RULES.md` §16 的规矩）。
- **推翻一条旧决策必须新写一条**：新条写清"取代 `ADR-nn`"与新的代价证据，旧条的 `状态` 改成 `被 ADR-N 替代` 并加一行指针，**旧条正文一个字都不改**——**不许原地改历史**。读的人要能同时看到"当初为什么那么定"和"后来为什么改"。
- **`接受` 不代表"这件事要做"**：`ADR-01 … ADR-14` 全是 `接受`，而它们的内容是**否决**（不做语义搜索、不做账号…）。`⛔` 说的是那件事被否决，ADR 的 `状态` 说的是这条记录有效。

### 2.3 一条 ADR 的固定字段

照抄 `templates/adr.md`。九个字段一个都不能少，尤其**后果要把坏的写出来**——只写好处的那条，下一个人会以为它没有代价：

| 字段 | 写什么 | 判据 |
|---|---|---|
| **编号 / 标题** | `ADR-nn` + 一句话；来自 `PRD.md` §6 的带 `← PRD ⛔D…` | 与 §3 总表一致 |
| **状态** | §2.2 那五种之一 | 被替代的要写清替代者编号 |
| **日期** | 本条**成文**的日期；决策本身的由来（spec / 批次 / 用户拍板）写在"背景"里 | 不编造原文没记的日期 |
| **背景** | 当时面对什么、谁提的、有没有事故 | 能追到 spec 节号 / 批次 / 用户拍板 / 源码注释 |
| **决策** | 定成什么样，一句话说清 | 与 `ARCHITECTURE.md` as-built 不矛盾 |
| **后果** | **好的与坏的都写**；坏的照抄文档里的"代价 / ⚠️" | 至少写出一条代价 |
| **考虑过的替代方案** | 还想过什么、为什么没选 | 抄现有文档给的理由，不自创 |
| **复核触发条件** | 什么信号出现就该重看（对应 ⬜ 的触发条件） | 与 §6 汇总表一致 |
| **关联 FR 与文档 §** | `FR-xxx` + `文档 §N` | 至少一处 |

### 2.4 推翻一条旧决策：五步

1. **先判定是哪一类**（§2.1 六条里的哪一条）。只是"现状描述错了"不写 ADR，改 `ARCHITECTURE.md`。
2. **写新 ADR（`提议`）**，指名取代 `ADR-nn`，把新证据与旧决策的代价一起写出来。
3. **过门禁**：涉及 `⛔` 的先改 `PRD.md` §6；涉及逐字文案的走 `REBUILD.md` §5 的五步门；涉及 schema 与备份格式的先读 `REBUILD.md` §2 与 `RELEASE.md` §5。
4. **新条转 `接受`、旧条转 `被 ADR-N 替代`**，两条互加指针，§3 总表与 §6 汇总表同步。
5. **留痕落点**：`CHANGELOG.md` 记一行（谁、判了谁错、改了什么），并把受影响那条 FR 的状态改掉。

## 4. 逐条 ADR（正文）

`ADR-01 … ADR-14` 是 `PRD.md` §6 那 14 条否决项的结构化版本（编号映射写在标题里）；`ADR-15 … ADR-24` 是从 `ARCHITECTURE.md` §15 与 `REBUILD.md` §2 提炼出来的 as-built 决策，**编号接着排**，来源写在各自"背景"里。

### 4.1 ADR-01 ← PRD ⛔D1：不做语义向量搜索 / FTS5 / 以图搜图

- **状态**：`接受`（否决项，长期有效） · **日期**：2026-10-07 成文；决策出自 spec §3 的"重要取舍"与 spec §1 的非目标
- **背景**：中文子串检索是主场景，而 FTS5 默认的 `unicode61` 分词器**把连续中文当作一个 token**，中文检索直接失效。
- **决策**：搜索 = 派生列 `search_text`（`data/db/SearchTextBuilder.kt`）+ 单列 `LIKE`（`Daos.kt:32-33`），排序在内存里按命中字段强弱（`ItemRepository.kt:209`、`domain/SearchRanker.kt`）。不做 FTS5、不做语义向量搜索、不做以图搜图。
- **后果**：好的 —— 中文子串天然命中，代码量少一大半，个人量级 `LIKE` 几十毫秒够用，"将来要换也不亏：**改动封在 `ItemDao` 一个方法里**"。坏的（代价）—— 候选上限 `LIMIT 300`，而且**截断发生在打分之前**（`RULES.md` §15 W4），界面还不说"还有更多"（🟡 `FR-FND-07`）。
- **考虑过的替代方案**：FTS5 默认分词器（中文失效）；"要做对得**自建 bigram 索引列**"，现在不值（spec §3）；语义向量搜索、以图搜图、拍照找物（spec §1 非目标，同一批否决）。
- **复核触发**：库里物品接近 300 件，或用户报"明明有却搜不到"；**且**要同时满足"查询串普遍 ≥3 字"（见下） · **关联**：`FR-FND-01`、`FR-FND-07`、`RULES.md` §10、`PRD.md` §6 D1、`TECH_STACK.md` §8.2 更正一
- 🔎 **2026-10-07 联网核实把这个结论加强了（从"够用"升级为"对中文更合适"）**：`trigram` 分词器的官方原文是"少于 3 个 unicode 字符的子串在全文查询里**不匹配任何行**"，而中文的主场景恰恰是 1–2 字词（「外套」「护照」）；`trigram` 还需要 SQLite ≥ 3.34（2020 年），minSdk 26 设备的系统 SQLite 拿不到，要用就得自带 `androidx.sqlite:sqlite-bundled`；Room 侧也只有 `@Fts3`/`@Fts4`（`room-runtime-android-2.8.5` 的 classes.jar 里没有 `Fts5` 注解）。→ **`LIKE '%q%'` 保持不动**，`TECH_STACK.md` §4 的 T4 因此从"可迁移"改成"默认不做"。

### 4.2 ADR-02 ← PRD ⛔D2：不用递归 SQL 建位置树

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 spec §5 `location_node` 一节与 spec §11 的 [待确认] 第 2 条
- **背景**：位置总量"几十到几百个"，而各版本 Android 内置 SQLite 对 recursive CTE 的支持不一致。
- **决策**：`LocationTree` 一次全量读入内存建树、算路径、判环（`LocationTree.kt`；`roots()` 把"父节点不存在"的脏数据也当根）。
- **后果**：好的 —— "一次全量查出内存建树更简单"，且**规避各版本 SQLite 对 recursive CTE 支持差异**；防环与脏数据都在纯 Kotlin 里处理，能直接 JVM 单测（`LocationTreeTest` 11 例）。坏的（代价）—— 每次建树都是整表读 + 内存计算（`LocationRepository.kt:149`、`:170-173` 的注释就是"树已在内存里，不必递归 SQL"）；位置候选 `selectablePaths()` **没有条数上限**（⬜ `FR-LOC-08`）。
- **考虑过的替代方案**：递归 SQL / recursive CTE —— 支持差异摆在那里，且把防环逻辑下沉进 SQL 后不好测。
- **复核触发**：路径数到几百条，或选择器一屏滚不完 · **关联**：`FR-LOC-08`、`RULES.md` §8.5、`PRD.md` §6 D2

### 4.3 ADR-03 ← PRD ⛔D3：不建"待归类"独立表

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 spec §11 的 [待确认] 第 3 条
- **背景**："待归类"看起来像一个收件箱，容易被做成第五张表。
- **决策**：它是**一个谓词**：`locationId IS NULL OR status = 'DRAFT'`（SQL 版 `Daos.kt:34-35`、内存版 `ItemRepository.kt:333`、界面版 `GalleryScreen.kt:324`）。独立表**会和真实位置状态打架**。
- **后果**：好的 —— 不存在"独立表和真实位置状态打架"这件事；"没放好位置"和"没确认"两种"没办完"用同一个谓词表达（`RULES.md` §1.1 记着为什么是**或**）。坏的（代价）—— 谓词有**已知不对称**：`locationId` 指向一个已不存在的节点时，卡片上写「待归类」而它进不了待归类页（`RULES.md` §1.1 📌，正常走不出这个形状）。
- **考虑过的替代方案**：独立 `inbox` 表 —— 与真实位置状态会分叉，还要处理"搬进位置了但表里没删"这一类不一致。
- **复核触发**：待归类需要自己的字段或历史（比如"什么时候进的箱"）· **关联**：`FR-FND-04`、`RULES.md` §1.1、`PRD.md` §6 D3

### 4.4 ADR-04 ← PRD ⛔D4：不做主题 / 动态取色设置项

### 4.6 ADR-06 ← PRD ⛔D6：不做回收站 / 软删除

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 spec §1 的非目标与 spec §8 的"删除物品"一行
- **背景**：删除是唯一不可逆的用户动作，常见做法是软删除 + 回收站。
- **决策**：删除用**二次确认**兜住（`FR-OPR-04`），确认框的话按照片共用情况分四档（`UiFormat.kt:25-33` 的 `deleteWarningOf`）。没有回收站，`delete` 就是真删（`ItemRepository.kt:282-289`：先删行、再按引用计数删文件）。

- **复核触发**：用户真的删错过一件要紧东西（那要先讨论回收站，而不是先加二次确认） · **关联**：`FR-OPR-04`、`RULES.md` §9、`PRD.md` §6 D6

### 4.10 ADR-10 ← PRD ⛔D10：不用端侧大模型

### 4.13 ADR-13 ← PRD ⛔D13：一张照片里"同一件的多角度"不当多件处理

- **背景**：一张照片里可能既有并排的多件物品，也有同一件物品的多个角度。
- **决策**：只按"并排的多件"分槽位，提示词最多列 4 件（`Prompt.kt:19`）；多角度明确列为非目标，属于 `FR-SRC-08`。

### 4.14 ADR-14 ← PRD ⛔D14：「不要这件」不加二次确认

- **状态**：`接受` · **日期**：2026-10-07 成文；用户拍板（spec 未记具体日期）
- **背景**：多件录入时槽位芯片旁有一颗「不要这件」（`ReviewScreen.kt:138`）。

### 4.17 ADR-17：确认页与详情页用 `return` 整屏接管，不叠层

- **背景**：外壳只有一颗 FAB 与底栏四格；录入页与详情页都是"从某一屏进去办事"的页面。
- **决策**：`if (reviewOpen) { … return }` 与 `detailId?.let { … return }` 提前接管整屏——底栏和 FAB 在那两屏**根本不进组合**。
- **后果**：好的 —— "那两屏没有'再切个 tab'的语义，留着底栏反而给了用户一条**绕过退出确认的后门**"；返回键四层优先级因此能排成一张表（`REBUILD.md` §2 第 8 行）。坏的（代价）—— 屏幕选择的**代码求值顺序就是优先级**，新增一屏时要想清楚它排在哪一支之前/之后（`ARCHITECTURE.md` §11.2 那张方块图就是为此存在的）。
- **考虑过的替代方案**：做成叠层 / 保留底栏 —— 会留下绕过退出确认的入口；也会让"录到一半切个 tab 再回来"这种状态变得要处理。
- **复核触发**：换导航框架，或改动外壳结构 / 返回键优先级表 · **关联**：`UI.md` §1.1、§2.3、`REBUILD.md` §2 第 5、8 行

### 4.18 ADR-18：取景屏必须是叠层，不替换底下那屏

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 `WheremyRoot.kt:188-189` 与 `:253-254` 的源码注释
- **背景**：取景屏要从"照片从哪来"弹窗或录入页上的「换一张」进来。
- **决策**：`viewfinder()` 是**叠层**，挂两次（录入页里面 `WheremyRoot.kt:262`、Scaffold 外面 `:394`，连底栏和 FAB 一起盖住）。
- **后果**：好的 —— "录入页一被 dispose，`liveReviewVm` 就清空"，叠层让「换一张」仍然是**同一件物品**（走 `replacePhoto`），不是新建一件。坏的（代价）—— 一个屏幕要在两处挂；`liveReviewVm` / `liveTreeVm` 只能是 `remember` 而**不能** `rememberSaveable`（它们靠活在组合里把照片投给当前那个 VM），所以进程被杀后只能退回原页面（`REBUILD.md` §2 第 6 行记了这条恢复语义）。
- **考虑过的替代方案**：用替换（`return` 一整屏）—— "拍完那张会被当成**新建一件物品**，而不是换掉这一件的照片"。
- **复核触发**：改动外壳结构，或新增第二个"照片从哪来"的入口（照片路由只有 `deliverPhoto` 一处收口） · **关联**：`FR-SRC-04`、`UI.md` §1.1、`REBUILD.md` §2 第 7 行

### 4.19 ADR-19：`domain/` 不引入 spec 里的四个转发类

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 `ARCHITECTURE.md` §15 的"§4 目录"一行
- **背景**：spec §4 的目录里列了 `SaveItemUseCase`、`SearchItemsUseCase`、`BuildLocationTreeUseCase`、`BackupUseCase` 四个"用例类"。
- **决策**：**不建这四个类**——确认与搜索落在 `ItemRepository`，建树落在 `LocationTree`，备份落在 `BackupRepository`；`domain/` 只留真正纯的 8 个（`CaptureFlow`、`LocationTree`、`SuggestLocationUseCase`、`ReminderEngine`、`AnalyzePhotoUseCase`、`SearchRanker`、`CameraGate`、`LocationTreePolicy`）。
- **后果**：好的 —— "**少一层空壳转发**"：每个用例类都只是把一次 repo 调用换个名字，去掉之后 `ItemRepository` 是唯一收口，纯逻辑仍能在 JVM 直接单测。坏的（代价）—— "同一个业务动作的入口"不再集中在一层：找"确认这件事从哪进去"要按层查（这正是 `ARCHITECTURE.md` §15 要专门留一行说明的原因）。
- **考虑过的替代方案**：照 spec 建四个转发类 —— 收益只是目录整齐，代价是多四个只转发不决策的类。
- **复核触发**：用例入口多到需要收口（那时新写 ADR，而不是"顺手补回 spec 的目录"） · **关联**：`ARCHITECTURE.md` §15、`REBUILD.md` §4 第 6 条

### 4.20 ADR-20：`CameraShutter` 接口里不出现 CameraX 类型

- **状态**：`接受` · **日期**：2026-10-07 成文；理由写在 `data/camera/CameraShutter.kt:3-8` 的 KDoc
- **背景**：取景屏要在没有相机的 JVM 里被测，而 CameraX 的 `ProcessCameraProvider` 一挂上去就永远等不到回调（`di/AppContainer.kt:43-46`）。
- **决策**：接缝是 `interface CameraShutter { suspend fun capture(): ByteArray? }`——**要么给 JPEG 字节、要么 null，不抛**；CameraX 只活在实现侧（`CameraXSource`），容器给默认实现、测试给假的。
- **后果**：好的 —— "取景屏因此能在没有相机的 JVM 里被测"（`CameraScreenTest` 9 例、`CameraWiringTest` 2 例）；换相机库时接口不用动。坏的（代价）—— 真正的相机那一层没有 JVM 用例，由真机自验覆盖（`CameraXSource` 的 KDoc 写明"这一层没有 JVM 用例，由批次 AQ 的真机自验覆盖"）。
- **考虑过的替代方案**：接口里直接用 CameraX 类型 —— JVM 里打不开相机，用例直接卡死。
- **复核触发**：换掉 CameraX（接口应当不需要改；要改说明接缝漏了类型） · **关联**：NFR-05、`ARCHITECTURE.md` §11.3、`REBUILD.md` §3 M6

### 4.21 ADR-21：AI 永远是增强项，失败只降级不阻塞

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 spec §4 与 `RULES.md` §13
- **背景**：无网、无 key、额度耗尽、模型返回垃圾，这四种在真实使用里都会发生。
- **决策**：**先落库再分析**（`CaptureFlow.kt:54-61`，`onDraftSaved` 在物品行落地之后、网络请求之前）；AI 失败只等于"少一些预填"，原因映射成 11 类中文文案（`ui/common/UiFormat.kt:35-56` 的 `failureText`），每条都带**下一步**（spec §8）；未配 key 时静默跳过（`NO_CONFIG`），运行时不切换实现（`di/AppContainer.kt:75-79`）。
- **后果**：好的 —— `G4` 成立（无网 / 无 key / 额度耗尽 / 返回垃圾时录入与查找照常可用）；"保存比 AI 快"这条主路径能兑现（批次 X 的事故就是为它立的判据）。坏的（代价）—— `G1` 的"3 秒"只对用户的**手**成立：AI 那一路最坏约 30 秒（15 秒超时 × 最多 2 次）后才有结果或降级手填，界面永远不会替用户等第三次（`PRD.md` §1.1 与 §5.1）。
- **考虑过的替代方案**：等 AI 完事再开行 / 把 AI 当流程闸门 —— `RULES.md` §17.1 的裁决是"**'先落库'赢，垃圾由退出时的空壳回收处理**"；反过来会把"保存比 AI 快"这条主路径废掉。
- **复核触发**：有人提议让 AI 自动确认或自动落库（那就撞上 G1 与这条裁决） · **关联**：`FR-AI-02`、`FR-AI-06`、`RULES.md` §3/§13/§17.1、`REBUILD.md` §3 M3

### 4.22 ADR-22："界面每一句话都必须真的成立"是最高纪律

- **状态**：`接受` · **日期**：2026-10-07 成文；纪律出自 NFR-02，判据在 `RULES.md` §16，操作步骤在 `REBUILD.md` §5
- **背景**：历史上有五句"说了没做"或"做了没说实话"被逐个改掉：待归类语义、退出弹窗对 CONFIRMED 说话、删除框对共用照片说话、"不保存直接离开"真的不留东西、位置候选提示。
- **决策**：新增或修改任何一句界面文案前，先问"这句话在**每一条**分支上都成立吗？"；可检验判据十条（`RULES.md` §16），动文案要过五步门（`REBUILD.md` §5：列全守卫条件 → 数清承诺了什么 → 先写会红的测试 → 看形状 → 同步四处文档）。
- **后果**：好的 —— 文案与数据层被钉在一起：`deleteWarningOf` 四档、`failureText` 11 条、位置话三句、"每档说法都要有能到达它的数据状态"。坏的（代价）—— 写一句话的成本很高（要懂守卫条件、要变异验牙），而且**已知未闭的两条还挂着**（`RULES.md` §15 W8 磁盘满时英文 `IOException` 原样上屏；W3 频道静音仍算已提醒）。它们"不是假话，是说了但说得不够准"。
- **考虑过的替代方案**：一句话盖住多种情况（省事）—— `RULES.md` §17.2 的裁决是"**诚实赢**：多写两档文案、多带一个计数器、多查一次 `photoDeletionOf`，都比一句假话便宜"。
- **复核触发**：每次新增 / 修改一句界面文案；修 W8 时按 `operate()` 的白名单写法补，**别把 `operate()` 放宽** · **关联**：NFR-02、`RULES.md` §16/§17、`REBUILD.md` §5

### 4.23 ADR-23：空壳只在退出录入页时回收，不加开机清扫

- **状态**：`接受` · **日期**：2026-10-07 成文；决策出自 `RULES.md` §1.4 的 📌 与批次 Z 的拍板
- **背景**：选图那一刻就落库（ADR-21），所以"选了照片又什么都没填就退出"会留下一具**空壳**。
- **决策**：空壳的定义是四个条件同时成立（`ReviewViewModel.kt:45-46`：`itemId != null && !saved && name.isBlank() && touched.isEmpty()`），**只在退出录入页那一次**回收（`closeWithoutAsking`，连照片文件一起摘掉，走既有引用计数）。`WheremyApp.onCreate` 只建通知频道 + 补 `search_text`。
- **后果**：好的 —— 不"在用户没开口的前提下删东西"，因为"**他还会回来接着填**"是常见情形；空壳判定只有两个读者（回收器与退出框里那句"会留下什么"），所以它待在一个地方。坏的（代价）—— 用户强杀进程或系统杀进程时，一具空壳会作为「未命名物品」留在待归类里，只能他自己删；这是拍板过的现状而不是待修项。
- **考虑过的替代方案**：开机清扫 / 启动时扫库 —— 等于替用户决定丢弃，而"他还会回来接着填"更常见。**重做时不要顺手加一个启动清扫。**
- **复核触发**：强杀留下的空壳多到影响使用（那时也先问用户） · **关联**：`FR-REV-06`、`RULES.md` §1.4/§6.4、`PRD.md` §2 状态机

### 4.24 ADR-24：频道静音仍算"已提醒"，保持现状

- **状态**：`接受`（钉住现状） · **日期**：2026-10-07 成文；决策出自批次 V（2026-10-03）的拍板，理由写在 `ReminderWorkerTest.kt:161-163`
- **背景**：`canNotify`（`ReminderWorker.kt:78-79`）只看运行时权限与系统总开关 `areNotificationsEnabled()`，**不看频道重要性**；于是用户把「到期提醒」这一个频道单独静音时，这一批仍会被回写成"已提醒"。
- **决策**：保持现状。理由是"**人静音的是声音，不是那条会留在通知栏里的提醒**，所以物品要被标记成已提醒"；测试明确钉住这个行为（`mutedChannelStillCountsAsDelivered`，"这条钉子是给'顺手把静音也当成发不出去'的下一次改动准备的"）。
- **后果**：好的 —— 只有一格通知，静音是用户自己的选择；不去替用户猜"他到底想不想收到"。坏的（代价）—— 频道静音时用户收不到、而这批**不会**被再说一次（`RULES.md` §15 W3 照实记为已知偏差）。
- **考虑过的替代方案**：把频道静音也当成"发不出去"（那就不回写 `expireNotifiedAt`）—— 没选；**改它要先问用户**（`REBUILD.md` §7 D3），并与 ADR-22 里"发不出去就不回写"那条（看的是权限与总开关）分清。
- **复核触发**：用户抱怨"静音了还被算作说过"，或要求按频道区分 —— 先问用户，不自作主张改 · **关联**：`FR-EXP-06`、`RULES.md` §11.4/§15 W3、`PRD.md` §1.1 G4

### 4.25 ADR-25：技术选型——官方推荐优先、成熟第三方次之，自造必须给证据

- **状态**：`接受` · **日期**：2026-10-07（**用户拍板**："技术架构和选择，我倾向于使用官方推荐的最佳实践，或者第三方的优秀的最佳实践，尽量不要自己造轮子"；并要求"多从网络/GitHub 等技术网站搜集，找出最佳组合"）
- **背景**：现有栈里 Room / DataStore / WorkManager / CameraX / kotlinx.serialization / OkHttp / Coil / Robolectric 已经是官方或社区最佳实践；但**依赖注入、导航、界面文案资源、搜索**四处是自造（`di/AppContainer.kt`、`ui/WheremyRoot.kt`、硬编码 Kotlin 文案、`LIKE` + 内存打分）。四处当初各自的理由（少一层空壳转发、一条命令就能测、文案即断言、中文 FTS 分词不可靠）在**局部**都成立，合起来却带来三样长期成本：① 与官方文档/示例脱节，接手的人找不到参照物；② 每加一个接入点（新的状态、新的注入、新的路由）都要手写一次；③ 评审时无法区分"这是有依据的取舍"还是"当初懒得找库"。
- **决策**：把选型默认顺序定成 **平台/官方 API → AndroidX/Jetpack/Kotlin 官方库 → 成熟第三方 → 自造**（`TECH_STACK.md` §1 的 P1–P5）；自造只在三种情况下允许（没有合适的库、有库但代价明显不划算、**需求语义库给不了**），并且**必须写成本 ADR 并给出复核触发条件**；现存自造件逐条判定（✅保持 / 🟡可迁移 / 🔒保留+理由 / ⬜待评估）与迁移队列 T1–T8 见 `TECH_STACK.md` §3/§4。
- **后果**：好的 —— 技术栈与官方方向一致，新人按官方文档就能上手；构建、测试、CI 都能直接用成熟方案；"不造轮子"第一次有了可执行判据（`TECH_STACK.md` §5 的五项体检）。坏的（代价）—— 迁移要花钱，且**高风险集中在两处**：T2（Hilt）动装配层，T3（Navigation）动外壳路由，而返回键四层、整屏接管、取景屏叠层、九格恢复语义、单一照片路由这五条 🔒 交互语义**现在全靠 `WheremyRoot.kt` 表达**——T3 之前必须先把它们写成回归测试（`WheremyRootTest` 20 例是基线）。
- **考虑过的替代方案**：① **不改，维持"够用就自己写"** —— 没选：与用户偏好相反，且长期成本已经在"每加一处接线就改容器"上显现；② **一次性全换**（DI + 导航 + 资源 + 搜索一起）—— 没选：五条 🔒 交互语义一次性重写等于赌一次大重构，出错时无法定位是哪一处换坏的；③ **先做收益高、风险低的那条**（文案资源化 T1：运行时文字不变，按文字断言的测试不受影响）—— **选了它**，队列顺序 T1 → T2 → T3（`TECH_STACK.md` §4）。
- **复核触发**：官方推荐发生变化（例如官方换了默认的 DI 或导航方案）；或 `TECH_STACK.md` §4 里任一 T 条目的触发条件被击中 · **关联**：`TECH_STACK.md`（全文）、`ADR-05`、`ADR-16`、`ADR-01`、`ADR-07`、`REBUILD.md` §2 第 10/11 条、`PRD.md` NFR-07、`PROCESS.md` §3.6
- 🔎 **2026-10-07：联网核实已完成一轮**，结果全部落进 `TECH_STACK.md` §8（官方口径原文、上游最新版本对照、引用来源），其中**改动了三处先前判断**：① 搜索不上 FTS（`ADR-01` 加强，T4 改为"默认不做"）② 导航迁移的目标从 Navigation Compose 改为 **Navigation 3**（1.2.0 已 stable）③ CI 的前置是**提交 Gradle Wrapper**（新增 T10），与本机"不生成 wrapper"的现状并存。还新增了 T9/T11–T15（静态检查、截图回归、纯版本 bump、AGP9/Gradle9/Kotlin2.4 大版本、性能发布配置、依赖更新自动化）。仍未验证的项在 §8.6。

## 7. 常见误读：这些不是笔误，是决定

容易被"顺手统一掉"的东西。每一条都写清出处，动手之前先读那一节。

1. **照片墙没有"默认排序"。** 空查询走 `itemDao.all()`（`Daos.kt:31`，**没有 `ORDER BY`**），`SearchRanker.kt:8` 遇到空词把列表原样退回——所以浏览态的次序是 SQLite 的 rowid 序（插入序，新录的排在最后），而 `ORDER BY updatedAt DESC` 只存在于四条带条件的查询里。真机上这条被踩过两次（新录的物件在屏幕外，看起来像"没录进去"）。出处：`RULES.md` §10.1/§10.2、`PRD.md` `FR-FND-09`。
2. **`lastMovedAt` 的两条写路故意不对称。** `confirm` 走三档判断——位置真的变了才写新时刻，没变就保留旧值（`ItemRepository.kt:159-163`）；`move` 走 `itemDao.moveTo`，**无条件**写（`Daos.kt:40-41`）。别"顺手统一"成两边都判等。出处：`RULES.md` §2 第 3 点。
3. **标签筛选认的是 `item_tag` 里的行，不是 `search_text` 里的字面。** 描述里提过一次"冬装"不代表这件打了冬装标签；chip 点下去多出一堆没打标的东西就是骗人（`ItemRepository.kt:212-213`）。出处：`RULES.md` §10.1。
4. **两个 `false` 都不是失败。** `changeParent` 返回 `false` 说的是"**本来就在这层**"（`LocationRepository.kt:73`，界面据此说"已经在这一层级，没有改动"）；`shiftWithinParent` 返回 `false` 说的是"**走到边界**"（`:160`）。出处：`RULES.md` §8.2/§8.4、§16.9。
5. **「保存改动并留下」就是「稍后处理」。** 两者内部都走 `keepForLater`；不许为退出弹窗新造第二种落库语义——"同一个动作在两个入口有两种落库方式，迟早只有一边是对的"。出处：`RULES.md` §6.3、§17.4。
6. **`LIMIT 300` 截断在打分之前。** SQL 先按 `updatedAt DESC` 砍到 300 条候选，再进内存打分；所以超出的那部分**根本没参与打分**，不是"打了分但排在后面"。出处：`RULES.md` §10.1、§15 W4。
7. **多件共用同一对照片文件，缩略图一样是对的。** `newDraftSharingPhoto` 复制源行的 `filePath`/`thumbPath`（`ItemRepository.kt:65-75`），所以一次录入的四件在照片墙上显示同一张图不是 bug。文件去留只有一条规则：**再没有任何照片行指着它，才从磁盘删**（`PhotoReclaim.kt:15-21`）。出处：`RULES.md` §4、§9.2。
8. **待归类页走内存谓词，不是那条 `inbox()` SQL。** `ItemRepository.inbox()`（`:218`）在 `app/src/main` 里**没有任何调用点**，只有测试在用；页面实际是 `GalleryViewModel` 的 `onlyInbox = inboxMode || filters.onlyInbox`。别把这一页接回 `inbox()`——那会绕掉搜索框与其余筛选条件的叠加。出处：`RULES.md` §1.1 ⚠️。
9. **同一个信息在位置页与照片墙是两种写法，别抄成一样。** 位置页的物品行是"**在** X"（`ItemRow.kt:63`，唯一调用点 `TreeScreen.kt:130`）；照片墙是裸路径或「待归类」（`GalleryScreen.kt:324`）。到期话术同样两套：照片墙"还剩 N 天 / 今天到期 / 已过期 N 天"（`UiFormat.kt:7-11`）vs 位置页"到期 yyyy-MM-dd"（`ItemRow.kt:62`）。出处：`PRD.md` `FR-FND-02`、`FR-EXP-08`。
10. **"发不出去就不回写"与"频道静音仍算已提醒"并存不是矛盾。** 前者看的是运行时权限与系统总开关（`ReminderWorker.kt:78-79` 的 `canNotify`），后者是**频道级**静音——批次 V 拍板保持现状，测试钉住；改它要先问用户。出处：`RULES.md` §11.4、§15 W3。
