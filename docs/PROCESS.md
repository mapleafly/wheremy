# Wheremy 开发流程与变更管理（PROCESS）

**这份文档回答**：一次改动从想法到发布要走哪些步、每一步的产出标准是什么、"改了这一处"必须同步改哪几份文档、什么情况下**不许**合并。
**它不回答**：测试怎么写（`TESTING.md`）、环境怎么搭（`DEVELOPMENT.md`）、包怎么出（`RELEASE.md`）、规则怎么算（`RULES.md`）。

**适用范围**：所有人、所有改动，包括"我就改一句话"和"我就删一个按钮"。
**本位**：本文是流程的权威出处（`README.md` §3.1）。本文与其它文档冲突时以本文为准；本文与事实冲突时以事实为准并改本文。

---

## 0. 三条总原则

### 0.1 文档先行（对规则、文案、门禁三类改动）

**先改文档 → 再改测试（此时必须红）→ 最后改代码（转绿）。**

理由是这个项目的特殊约束：界面测试**按文字找节点**（`REBUILD.md` §2 第 9 条），逐字文案在 `RULES.md`/`UI.md` 里各有一份抄本。先改代码会让"文档、测试、代码"三者同时漂移，事后谁也证明不了谁是对的。三类改动的具体走法见 §3.2、§3.4。

其余改动（重构、依赖升级、缺陷修复）允许代码与文档同批提交，但**同批**这两个字不能省。

### 0.2 一处信息只有一个出处

见 `README.md` §3.1 的唯一事实源表。改信息时**只改权威那一份**，其它文档留指针（§ + 一句"见 X"），不许复制第二份真值。
已经在 `RULES.md` §16 第 8 条写下的同理："不抄第二份真值"——超时秒数不进文案、提前天数不进文案常量、`classify` 是唯一映射。

### 0.3 诚实优先于省事

NFR-02："界面上每一句话都必须真的成立"（判据 `RULES.md` §16，真实裁决 `RULES.md` §17）。
落到流程上就是一条：**任何一次"说了但做不到"的实现，必须在同一次改动里改成说得准，或者改成不说**。
不许用"先这样、以后再说"绕过——"以后"必须落成一个带触发条件的 ⬜ 条目（`PRD.md` §5），才算把它说清楚了。

## 1. 角色、职责与交接物

一个人可以身兼数角，**但每一格的产出必须留下来**（"用证据替代他人评审"是单人项目的替代条款，见 §8.3）。

| 阶段 | 主责角色 | 必须参与 | 交接物（有形） | 判据 |
|---|---|---|---|---|
| 需求立项 | 产品 | 软件经理 | `templates/feature-proposal.md` 填好的提案 + `PRD.md` 新增 FR（状态 `⬜`，带触发条件与代价） | DoR（§4.2） |
| 规则 / 界面定稿 | 架构师 + UI | 测试 | `RULES.md` 增补（含逐字文案与分支可达性）、`UI.md` 增补 | 每条新文案都能说出它在哪些分支上成立（`RULES.md` §16.3） |
| 实现 | 开发 | — | 代码 + 测试 + 可能的 `ARCHITECTURE.md` 增补 | 门 G0/G1（§6） |
| 测试与验牙 | 测试 | 开发 | 变异清单、判绿证据、覆盖对账 | 门 G2/G3 |
| 文档收口 | 提出改动的那个人 | 软件经理 | 同步矩阵（§5）逐行勾掉 | 门 G4 |
| 发布 | 软件经理 | 产品 | `templates/release-checklist.md` 签收 | 门 G5 + `RELEASE.md` §3 |
| 复盘 | 全员 | — | `CHANGELOG.md` + `DECISIONS.md` 增补 | 有可复核的结论 |

## 2. 需求的生命周期（FR 状态机）

### 2.1 状态与流转

```
                ┌──────────────── 任意状态 ────────────────┐
                ▼                                          │
  ⬜ 待做 ──开工──▶ 🟡 部分落地 ──验收通过──▶ ✅ 已落地      │
                │                                          │
                └─────────────────────▶ ⛔ 已否决 ◀─────────┘
                                     （必须写 ADR，见 §3.3）
```

- **谁改状态**：`⬜ → 🟡` 由开发在开工时改；`🟡 → ✅` **由测试确认后改**（理由：升 `✅` 的条件是"有具名测试守着"，那正是测试的产出，见 `PRD.md` §7）；`⛔` 由产品改，且必须同时在 `DECISIONS.md` 留一条 ADR。
- **`✅` 的两个必要条件**：① 有测试或真机自验覆盖（`PRD.md` §0 的记号定义）；② `PRD.md` §7 的"需求 ↔ 守门测试"索引里能找到具名测试类。
- **`🟡` 必须写清"差在哪一件"**，并同时出现在 `PRD.md` §5.1 一览表里（那张表决定"做到什么程度算做对"）。

### 2.2 FR 编号与四件必写的事

- 编号格式 `FR-<域>-<两位序号>`；域自增、**不复用已删编号**。现有域：`SRC` 照片来源、`AI` 识别、`REV` 确认与落库、`LOC` 位置、`FND` 查找、`OPR` 单项操作、`EXP` 到期、`BAK` 备份、`CFG` 设置、`TRC` 可观测、`PRM` 权限与适配、`DB` 数据迁移、`RLS` 发布。
- 每条 FR 至少四行：**要什么**（可测）、**状态**、**触发条件**（⬜ 必须有：什么信号出现时才动手）、**代价**（要动哪些面）。
- 非功能需求用 `NFR-nn`，同样给判据（现在的判据在 `RULES.md` §16 与 `REBUILD.md` §1）。

### 2.3 需求变更的三种形态

| 形态 | 落点 | 例子 |
|---|---|---|
| **新增** | 新 FR id | "AI 预填到期日"→ FR-AI-09 ⬜ |
| **修改** | 改现有 FR 的正文 + 状态回落 | "3 秒内完成录入"从 ✅ 改成 🟡 并把口径写清（`PRD.md` G1 就是这么改的） |
| **删除/否决** | FR 保留、状态改 `⛔`、理由写进 `DECISIONS.md` | ⛔D6 回收站、⛔D4 主题设置 |

**删掉一条 FR 时，`PRD.md` §3 的正文不删**——它连同否决理由留在原地，避免下次重新讨论（`PRD.md` §6 的开场白就是这个意思）。

## 3. 八条变更通道

每条通道的格式固定：**什么时候用 → 入口条件 → 步骤 → 必须动的文档 → 必须动的测试 → 验收 → 禁止项**。

### 3.1 通道一：新增功能（新 FR）

- **什么时候用**：用户提出新诉求，或 `PRD.md` 的某个 ⬜ 条目被触发条件击中。
- **入口条件**：`templates/feature-proposal.md` 填完；成功判据可测（能写出"怎么算做对了"）；不违反任何 ⛔（违反就先走 §3.3）。
- **步骤**：
  1. 提案 → 分配 FR id，`PRD.md` 记 `⬜` + 触发条件 + 代价；
  2. 判定它落在哪一层：规则（`RULES.md`）→ 界面（`UI.md`）→ 视觉（`DESIGN_SYSTEM.md`）→ 结构（`ARCHITECTURE.md`）。**每一层都要留下增补，不能只在代码里长出来**；
  3. 先写测试（红）：至少一条"没有这个功能就会红"的测试；
  4. 实现（`DEVELOPMENT.md` §8 的扩展点清单告诉你必改哪几个文件）；
  5. 变异验牙（§6 G2）；
  6. 更新 `PRD.md` §7 测试索引、`PRD.md` 状态、`README.md` §2（如果新增了文档）。
- **必须动的文档**：`PRD.md`（必然）、`RULES.md`（有规则时要）、`UI.md`（有界面时要）、`ARCHITECTURE.md`（有新的类/顺序不变量时要）。
- **验收**：该 FR 的验收方式逐条可执行，且在新装机的真机上能看到（若属于只能真机的部分，进 `REBUILD.md` §6 那张清单）。
- **禁止**：先写代码后补文档；把新功能藏在一个"顺手改"的提交里；给新功能加第二条流程（例如"这个功能不用测试"，不允许）。

### 3.2 通道二：修改一条已有行为

- **什么时候用**：现有行为不对、不够好、或需求变了。
- **入口条件**：能指出**现在被违反或被改掉的那一条规则**（`RULES.md` § 与逐字串）。
- **步骤（文档先行的标准流程）**：
  1. 改 `RULES.md` 的规则/文案（含"哪些分支会说这句话"的完整清单）；
  2. 改断言它的测试，**跑到红**（红是证据：证明这条测试真的守着那句话）；
  3. 改 `UI.md`（文案或次序变了）；
  4. 改代码，跑到绿；
  5. 变异验牙：把守卫条件反掉，期望**恰好那条**红；
  6. 评估连带：`PRD.md` 的 FR 状态要不要动、`RULES.md` §14 阈值表、§15 已知偏差表要不要加一行。
- **必须动的文档**：`RULES.md` + `UI.md`（逐字文案双抄本）+ 测试。**这三处必须同一次提交**。
- **禁止**：只改代码不改测试（等于让断言失守）；只改 `RULES.md` 不改 `UI.md`（下次有人按旧的抄本对账）；把"说得更准"的新句写成"说得更好听"（`REBUILD.md` §5 的第 2 步：数它承诺了什么）。

### 3.3 通道三：删除一个功能

- **什么时候用**：这个功能被判定有害、无用、或与新产品判断冲突。
- **入口条件**：**判定删的是什么**，三种只能选一种或多种：
  - **只删入口**（代码里的功能保留，界面不再给）→ 规则要写明"这个能力界面不提供"；
  - **删规则**（行为不再存在）→ `RULES.md` 整条划掉，并把它的判据表（`RULES.md` §18）同步；
  - **删数据**（字段/表/格式不再用）→ **高风险**，走 §3.7。
- **步骤**：
  1. `PRD.md` 状态改 `⛔` 并保留原文 + 理由（`DECISIONS.md` 写一条 ADR）；
  2. 找出所有提到它的文档（grep 全文，包括 `REBUILD.md`、`GLOSSARY.md`）逐处处理：删、或改成"已否决"的指针；
  3. 测试：删掉只守它的用例，同时补一条"它不再存在"的断言（防止以后再长回来）；
  4. 数据：**默认不删用户已有数据**。字段留着、界面不显示，是删除功能的默认形态；
  5. 用户可见的变化写进 `CHANGELOG.md`。
- **禁止**：删了功能却留着 `RULES.md` 里的规则（下一个人会照着规则把它做回来）；删数据却不评估备份兼容（老备份包导入会怎样）。

### 3.4 通道四：补充细节、调整文案与次序

- **什么时候用**：`⬜` 的触发条件被击中（补细节），或文案/次序被判定不准确/不好用。
- **入口条件**：文案类改动必须先过 `REBUILD.md` §5 的**五步门**：
  1. 找出这句话在哪些分支上会被说出来（把守卫条件全列出来）；
  2. 数它承诺了什么（每条都是可证伪的断言）；
  3. **先写一条会红的测试再改文案**；
  4. 看形状（与按钮同排的文字必须 `weight(1f)`，`REBUILD.md` §5 第 4 步）；
  5. 同步四处：`RULES.md` 逐字表、`UI.md` 🗣 小节、`PRD.md` 的 FR 状态、守门测试名。
- **必须动的文档**：同上四处 + `DESIGN_SYSTEM.md`（涉及排版规矩时）。
- **禁止**：把文案改动混进重构提交；用"更顺口"当理由（理由必须是"更准确"或"原来的话不成立"）。

### 3.5 通道五：重构（行为不变）

- **什么时候用**：结构需要改善（例如 `REBUILD.md` §4 列的六条分离）。
- **入口条件**：**先用测试把现状钉死**。钉不住的地方，先补测试，或者缩短范围。
- **步骤**：
  1. 列出"绝对不许变"的行为清单（从 `RULES.md` 的 🔒 条目里挑）；
  2. 在全绿基线上做重构（`TESTING.md` §6 判绿）；
  3. 全量回归（不是只跑改到的类）；
  4. 若 `ARCHITECTURE.md` 描述的类、方法、顺序变了 → 同批更新；
  5. 提交信息写 `refactor:`，并在正文里写明"行为不变的证据 = 全量 481 例全绿 + 无新增字段"。
- **禁止**：顺手改行为（那是通道二）；顺手改文案（那是通道四）；重建期顺手改 schema（那是 §3.7）。

### 3.6 通道六：依赖与工具链升级

- **什么时候用**：安全更新、被平台逼迫（targetSdk）、或某个库的新能力正好解决一条 ⬜。
- **先过选型准则**（`TECH_STACK.md` §1）：**官方推荐方案优先 → 成熟第三方 → 实在没有才自造**；
  自造必须写 ADR 并给复核触发条件（`TECH_STACK.md` §1 P3/P4）。判断顺序与"该不该加这个库"的体检清单在 `TECH_STACK.md` §5。
- **步骤**：
  1. **加依赖之前先答辩**：官方有没有？现有依赖能不能做？包体与依赖图代价多少（`TECH_STACK.md` §5 的五项体检）；
  2. 一次提交只升一条（或同一组强绑定的几条），版本只改 `gradle/libs.versions.toml`；
  3. 全量回归 + G2 变异抽查 + 真机冒烟（`REBUILD.md` §6 里受影响的那几条）；
  4. 涉及 Compose / Room / WorkManager 的升级，必须额外跑一次真机上的备份导入导出与通知链路；
  5. 更新 `ARCHITECTURE.md` §2 的版本表、`TECH_STACK.md` §3 的对照表与 `REBUILD.md` §8 的关键版本一行。
- **禁止**：一次升整张表；为了一个图标引 `material-icons-extended`；为了省事引 Hilt（⛔D5，**但这条已被 `TECH_STACK.md` T2 列入迁移队列**——迁移完成前现状有效）；**引入第二套同类库**（第二个 HTTP 客户端 / 第二个图片库 / 第二个 DI 框架，一律不准）。

### 3.7 通道七：schema 与备份格式变更（高风险）

**这是全项目唯一一条"错了就不可逆"的通道**，因为它同时踩三样东西：`REBUILD.md` §2 第 1 条（schema 冻结）、第 2 条（旧包必须还能导入）、以及用户的整机数据。

- **入口条件**：⭐⭐ 前置项已解决——`fallbackToDestructiveMigration(true)` 必须**先**换成真实 Migration（`PRD.md` ⭐FR-DB-01、`RULES.md` §15 W2）。**没有做完这一条，不许改 `@Entity` 的字段。**
- **步骤**：
  1. 写一条 ADR（`templates/adr.md`）：为什么必须改、改了之后旧数据怎么办、旧备份包还能不能导入；
  2. 设计迁移：`@Entity` 改动 → Room `Migration` → 升 `DB_SCHEMA_VERSION` → schema JSON 对比（`app/schemas/` 里有基线）；
  3. 写 **migration 测试**：从旧版本库升级到新版本，断言数据逐行还在；
  4. 备份兼容：包里的 `manifest.schemaVersion` 与导入侧的拒收规则（"来自更新的版本"）必须重新走一遍 `RULES.md` §12；
  5. 真机演练：装旧版本 → 录数据 → 导出 → 装新版本 → 导入 → 对账（物品数、位置数、照片文件数）；
  6. 更新 `REBUILD.md` §2 第 1/2 条的状态与 `RELEASE.md` §5 的兼容矩阵。
- **禁止**：跳过 migration 直接改字段（会静默清空整机数据）；改备份格式却不做"旧包还能导入"的测试；在发布窗口里顺带做这件事。

### 3.8 通道八：发布准备

见 `RELEASE.md` §3–§6。流程侧只记三条：
1. 发布必须逐条签收 `templates/release-checklist.md`；
2. G0–G5 全绿才算发布就绪（§6）；
3. 发布后 24 小时观察项没走完，不许开始下一个高风险改动（§3.7）。

## 4. 一轮迭代（批次）怎么跑

### 4.1 批次是什么

**批次 = 一次可独立验收、独立提交的改动集合**，提交信息说清"这一批改了什么、代价是什么"（`REBUILD.md` §9）。
经验边界：一次提交 ≤ 一个可验收的行为变化；一轮迭代 ≤ 一周；一次迭代里最多一条高风险通道（§3.7）。

### 4.2 五阶段与出口判据

| 阶段 | 做什么 | 出口判据 | 产出 |
|---|---|---|---|
| ① 计划 | 选条目、写计划、判断 DoR | 每条都有 FR id、验收方式、触发条件与代价；写作用域互不重叠 | `templates/iteration-plan.md` |
| ② 设计 | 需求 → 规则 → 界面 → 结构 逐层落文档 | `RULES.md`/`UI.md`/`ARCHITECTURE.md` 的增补写完，且**没有一条新文案说不出它什么时候出现** | 文档增补 |
| ③ 实现 | 先红后绿 | 改动的测试先红后绿；`RULES.md` 的 🔒 条目不违反 | 代码 + 测试 |
| ④ 自测与验牙 | 全量回归 + 变异 | G1 + G2 通过（§6） | 变异清单与判绿证据 |
| ⑤ 收口 | 文档同步 + 提交 + 复盘 | G3 + G4 通过；提交信息写清代价 | 提交 + `CHANGELOG.md` |

**DoR（Definition of Ready）——一条需求可以开工的四个条件**：
1. 有 FR id 与状态（`⬜` 或 `🟡`）；
2. 验收方式可执行（"怎么算做对了"能写成一条测试或一次真机动作）；
3. 触发条件与代价写清（对 ⬜ 条目）；
4. 影响面已识别：会碰到 `RULES.md` 的哪几条 🔒、需不需要真机、动不动 schema。

**DoD（Definition of Done）——一批改动算完成的六个条件**：
1. G0–G4 全绿（§6）；
2. 文档同步矩阵（§5）逐行勾掉；
3. `PRD.md` 状态与 §7 索引更新；
4. 真机部分（若有）已进 `REBUILD.md` §6 清单或已签收；
5. 提交信息写清"改了什么 + 代价/影响"；
6. `CHANGELOG.md` 有一行。

### 4.3 中断与插入

- **紧急缺陷**（P0/P1）可以直接插进当前批次，但**必须**：先写会红的测试、单独一次提交、回归范围写清（§7）。
- **临时插入的"小改动"**（改一句话）也算通道四，五步门一步不能省——历史证明这句话正是最容易变成假话的地方（`REBUILD.md` §5 的两个反例）。
- **被打断的批次**：留在工作树上的改动要么提交、要么回退；**不许把半成品留在下次迭代里**（半成品会让下一次判绿失去基线）。

## 6. 质量门 G0–G5

**门不是仪式，是"证据存在"的检查。** 每一门都要求一份能贴进提交或迭代记录的证据。

| 门 | 判据 | 证据长什么样 | 不通过怎么办 |
|---|---|---|---|
| **G0 构建** | `gradle :app:assembleDebug` 成功 | 命令行输出 `BUILD SUCCESSFUL` | 修到通过；**不许**在测试前用"构建应该没问题"跳门 |
| **G1 单测全绿（双证）** | ① `gradle :app:testDebugUnitTest` `BUILD SUCCESSFUL`；② 本轮 XML 的 mtime **晚于**本轮起跑时刻，且自数 `tests/failures/errors` | 一个 XML 计数（39 份、481 例、failures=0 errors=0）+ 一条"XML 比本轮新"的检查 | 见 `TESTING.md` §6；陈旧 XML、后台无 gradle、`GradleWorkerMain` 文件锁三种伪绿/伪红都要按 `REBUILD.md` §1.1 处理 |
| **G2 变异验牙** | 把改动的那一行**故意改坏**，期望恰好对应的测试变红 | 变异清单：改了哪一行 / 期望哪条红 / 实际哪条红；"无牙"的条目要补测试 | 补测试或删断言；`REBUILD.md` §1.3 里两条真无牙就是这么暴露的 |
| **G3 覆盖对账** | 正向：`PRD.md` §7 每行都有具名测试类且例数一致；反向：`@Test` 类数 = 42、总数 = 261（数字随批次增长，对账口径见 `TESTING.md` §5） | 两次 grep 的输出 | 缺口补测试；`PRD.md` §7 表随实现更新 |
| **G4 文档同步** | §5 矩阵逐行勾掉；没有文档说了、代码没做的事；没有代码做了、文档没写的事 | 勾过的矩阵 + 本次提交的文档 diff | 补齐；**不许**用"下次一起补" |
| **G5 真机人工清单** | `REBUILD.md` §6 那七条由**人**在真机上回"看到了什么" | 签收单（`templates/device-acceptance.md`） | 未签收不许对外交付 |

**豁免条款（只有一种）**：纯文档改动（不碰代码、不碰测试）可以只过 G4。
**豁免必须写在提交信息里**，一句话："本次仅文档改动，走 G4 豁免"。
除此以外没有豁免——**尤其没有"这次赶时间"**。

## 7. 缺陷流程

### 7.1 来源

四个来源，都必须留下证据：① 用户真机反馈；② 自审（读代码时发现"说了没做"）；③ G2 的"无牙"；④ G3 的对账缺口。

### 7.2 分级

| 级别 | 判据 | 处置时限 |
|---|---|---|
| **P0 数据损失 / 不可逆** | 用户数据被删、被覆盖、备份不可恢复、静默清库 | 立即停手 → 先取证 → 先导出 → 修 → 全量回归 |
| **P1 主线不可用 / 假话** | 录入或查找走不通；**界面上有一句话不成立**（NFR-02 违例） | 当轮迭代必修 |
| **P2 局部错误** | 某个分支不对、文案不精确、排序/统计偏差 | 下一个空闲批次 |
| **P3 体验与打磨** | 排版、措辞可改、无障碍缺口 | 与相关 FR 的 ⬜ 一起排 |

**P1 的特别说明**：文案不成立在本项目按 P1 处理，不是 P3。理由写在 `REBUILD.md` §5：这个 app 的价值就是"它说的话能信"。

### 7.3 处理步骤

1. 填 `templates/defect-report.md`（可照做的复现步骤 + 证据）；
2. **先写一条会红的测试**（P0/P1 强制；P2 尽量），红是"我找到的是真问题"的证据；
3. 修；
4. 变异验一次牙（证明这条测试真的守着它）；
5. 定回归范围：至少跑受影响类 + 全量（全量只有几百毫秒级的开销，没有省的理由）；
6. 判断要不要动文档：代码错 → 改代码；文案不成立 → 走通道四；文档错 → 直接改文档；**"钉住现状"的偏差** → 记入 `RULES.md` §15，注明已知未修；
7. 关闭判据写进缺陷单：哪条测试由红转绿、哪份文档改了哪一行。

### 7.4 紧急插单（hotfix）

P0/P1 允许插队，但三件事一件都不能省：单独提交、先红后绿、回归写清。
**用户的数据动作永远优先于修复速度**：任何会改手机上数据的操作，先问用户（`REBUILD.md` §9）。

## 8. 提交、分支与评审

### 8.1 提交粒度

- 一个可验收的行为变化 = 一次提交；**代码、测试、文档同批**；
- 文档与代码分开提交**只允许**一种情形：纯文档整理（走 G4 豁免）；
- 不许把重构与行为改动塞进同一次提交（评审时看不清哪一半改了行为）。

### 8.2 提交信息

```
<type>: <中文一句话，说清这一批改了什么以及代价>

（可选正文：为什么这么改、来源是哪条 FR/CR、验证方式）
```

`type` 只有六个：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`。历史批次号（AT/AU…）可以留作线索，但主体必须是人话（`REBUILD.md` §9）。

### 8.3 分支策略与评审

- **单人项目**（现状）：`main` 直提；**用证据替代他人评审**——每批必须留下 G1 判绿证据、G2 变异清单、涉及文案时的五步门记录。三样缺一，等于没有评审。
- **多人**：短分支 + 合并前跑 G1/G2；分支命名 `feat/fr-ai-09`、`fix/p1-通知点不进去`；合并用 squash，提交信息按 §8.2 重写。
- **评审清单（自评与他评共用）**：
  1. 改动的每一处，在 §5 同步矩阵里都能找到落点吗？
  2. 有没有新增/修改的界面文案？它的分支可达性证明在哪（`RULES.md` §16.3）？
  3. `RULES.md` 的 🔒 条目有没有被绕过？
  4. 有没有第二份真值被抄了出来（§0.2）？
  5. 判绿是不是**这一轮**的（G1 双证）？
  6. 提交信息说清代价了吗？

### 8.4 绝不提交

API key 或任何厂商 key 的字面值、`local.properties`、真机导出的 `data.json`、含隐私的截图与 dump、账号密码、`build/` 产物。
完整清单与理由见 `REBUILD.md` §9；这条是硬约束（`PRD.md` NFR-03）。

## 9. 例外、技术债与"暂时不做"

### 9.1 例外只允许一种形状

**有出处 + 有测试钉住 + 有归还动作**，三条同时成立才叫例外：

1. **有出处**：`PRD.md` 里一条 ⬜ 或 `RULES.md` §15 里一条已知偏差（W 编号）；
2. **有测试钉住现状**：行为被断言住，不是"没人管"；
3. **有归还动作**：代码里只允许一种 TODO 写法——
   ```kotlin
   // TODO(FR-XXX): 一句话说明差在哪、什么条件下做
   ```
   `FR-XXX` 必须在 `PRD.md` 里存在。`TODO` 不带 FR id 的一律视为技术债，G4 拦下。

### 9.2 技术债怎么看见

- `grep -rn "TODO(" app/src/main` 的结果应与 `PRD.md` §5 队列、`RULES.md` §15 已知偏差能对上；
- 每轮迭代开头扫一次；对不上的要么补出处、要么补归还动作；
- **不许**用"以后重构时会解决"当归还动作（那不是条件，是愿望）。

### 9.3 明确不许出现的例外

- 静默失败（`runCatching` 吞异常后不给用户任何说法——`PRD.md` FR-CFG-02 里那一处是**已知且被记录**的例外，不许再长第二处）。
- 假绿测试（没有变异验牙的断言；`REBUILD.md` §1.3）。
- 无出处的文案（说不出它什么时候出现）。
- 为绕过门禁而改测试（改断言让它变绿 = 造假证据）。

## 10. 流程自身的迭代

流程不是宪法，但改流程要付两样东西：**理由**和**影响面**。

- 改流程必须同批更新 `README.md` §5/§6 与本文受影响的 §，并在 `CHANGELOG.md` 写一行；
- **判"流程太重"的信号**：门禁的产出没人看、证据为了应付而编、一次小改动要走超过半天流程；
- **判"流程太轻"的信号**：同一类缺陷连续出现两次（说明少了一道门）、文档与代码连续两批不同步、发布后才发现该在 G5 发现的问题；
- 调整方向：**先加证据要求，再减步骤**——证据是唯一能替代"多一双眼睛"的东西。
