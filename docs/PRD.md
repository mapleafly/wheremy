## 1. 产品定位

**一句话**：把家里东西拍一张照，AI 替我记下它是什么、放进哪一层，日后我忘了自己有这东西时也能搜出来、找得到。

用户原始诉求里的关键一条把产品从"记得住东西在哪"扩展成"记得住自己有什么"：
> "我可能全然忘记了有哪些东西，比如想找一件深秋穿的外套，希望 APP 给出库存和照片。"

所以**照片墙（网格 + 按类别/季节/标签筛）是查找主视图**，不是列表的附属装饰；
而 AI 必须输出**可筛选的结构化字段**，不能只回一段自由描述。

### 1.1 成功判据（可测的）

| # | 判据 | 状态 | 说明 |
|---|---|---|---|
| G1 | 一件物品的录入在 3 秒内完成 | 🟡 | 照片选/拍下去**即刻落库**（✅）；AI 预填有**硬上限**：一次调用最多等 15 秒（`AppContainer.kt:62` 的 `callTimeout`，常量 `CALL_TIMEOUT_SECONDS = 15L` 在 `:102`），可重试的最多两次（`ApiPhotoAnalyzer.kt:174` `MAX_ATTEMPTS = 2`），所以**最坏约 30 秒后必然给出结果或降级手填**——界面永远不会替用户等第三次。目标态解释见下 |
| G2 | 30 秒内找到任意一件已录物品的存放路径 | ✅ | 搜索框打词 → 网格里看见缩略图、名称，和第三行的位置路径（裸路径"家 / 主卧 / 衣柜"，没有位置时同一行说「待归类」——`GalleryScreen.kt:324`；带"在"字前缀的那种写法只在位置页的物品行里，见 FR-FND-02） |
| G3 | 不记得自己有什么时，能按类别/季节翻出来 | ✅ | 照片墙筛选：类别、季节、标签、只有待归类、快到期/已过期 |
| G4 | 无网 / 无 key / 额度耗尽 / 返回垃圾时录入与查找照常可用 | ✅ | AI 永远是增强项，见 FR-AI-06 |
| G5 | 全部数据在本地，可一键导出、换机导入 | ✅ | zip 手动导出（FR-BAK），无云 |

**G1 的目标态口径**（这是产品判断，不是偷懒）：3 秒指的是**用户的手**——选完照片就能开始打字，不等 AI；
AI 是"帮你少打几个字"的加速器，不是流程的闸门。任何实现都必须保证：**AI 慢或坏，录入流程不卡住**。
判据落到两条可测的：① 照片到位的那一帧就出现可编辑表单（不等网络）；② AI 回来时不覆盖用户已经动过的字段。

### 1.2 使用者与场景假设

- **单人单机**。没有账号、没有多人共享、没有同步。
- 用户自己侧载 APK；开发期用一台小米 13 / HyperOS（序列号 `9aa4b43e`）做真机验收，很多行为判定以它为准。
- 数据量级：个人 + 家庭物品，几千条以内，照片几百到几千张。
- 使用节奏：一次录一批（收拾东西、换季、新买），平时只查不改。
- 手机常开，允许 WorkManager 每天跑一次后台任务；不允许常驻服务。

## 2. 概念模型

| 术语 | 是什么 | 落在哪 |
|---|---|---|
| 物品 Item | 一条"我有一件 X，它在 Y"的记录 | `item` 表，`data/db/Entities.kt:44` |
| 状态 status | `DRAFT`（还没确认）/ `CONFIRMED`（录完了） | `Entities.kt:9` |
| 待归类 Inbox | **不是一个表，是一个谓词**：没有位置 **或** 还是 DRAFT | `Daos.kt:34` |
| 位置节点 Location | 层级容器（家 > 主卧 > 衣柜 > 抽屉 > 收纳盒） | `location_node` 表，`Entities.kt:25` |
| 路径 path | 从根到该节点的显示串，` / ` 连接 | `domain/LocationTree.kt` `breadcrumb()` |
| 照片 Photo | 一次写入产出三档：原图 1600 / 缩略图 256 / 分析用 1024（后者不落盘） | `data/photos/PhotoStore.kt` |
| 主人 owner | 照片可以多态地挂在**物品**或**位置**上 | `item_photo.ownerType` 字段（`Entities.kt:71`）；取值常量在 `Entities.kt:11` 的 `PhotoOwner` |
| 标签 tag | 自由词，一行一个，用于筛选 | `item_tag` 表 |
| 别名 aliases | 逗号分隔的"我平时怎么叫它" | `item.aliases` |
| 到期 Expire | 保质期/保修/证件有效期，一个日期 + 一个种类 | `item.expiresAt` / `expireKind` |
| 容器猜测 containerGuess | 模型说"这东西一般放在哪种容器里"，本地拿去对树 | `data/vision/AnalysisResult.kt:13` |
| 槽位 slot | 一张照片里认出的多件物品，一件一个槽位 | `ui/review/ReviewViewModel.kt` |
| AI 留痕 trace | 每次尝试的提示词原文 + 模型回应原文，只留最近 10 条 | `data/vision/AnalysisTrace.kt` |

**状态机（必须照此实现）**：

```
（选/拍照片）→ 落库 DRAFT（无名字、无位置）
    ├─ AI 回来 → 覆盖模型明确给出的字段，仍 DRAFT
    ├─ 用户点「保存」 → CONFIRMED（名字必填）
    ├─ 用户点「稍后处理」 → 保持 DRAFT，进待归类
    └─ 用户退出且什么都没填 → 连照片一起删掉（不留空壳）
（手工搬进某个位置）→ 有名字的 DRAFT 顺手转 CONFIRMED；没名字的不转
```

实现：`ItemRepository.kt` `newDraft:31` / `applyAnalysis:109` / `confirm:152` / `keepAsDraft:183` / `move:242`；
空壳（什么都没填就退出）的定义与回收见 `RULES.md` §1.4 与 §6.4。

## 3. 功能需求

### 3.1 照片来源（FR-SRC）

**FR-SRC-01 从系统相册选一张照片录入** ✅
照片墙右下角那颗 +（`WheremyRoot.kt:328-332` 的 FAB，无障碍标签 `:330` 「选照片录入」；它在四个标签页都在）

**FR-SRC-02 在应用内取景拍照** ✅

实现：`ui/camera/CameraScreen.kt`、`ui/camera/CameraXSource.kt`、`domain/CameraGate.kt`。

**FR-SRC-03 拍照/选图二选一的来源弹窗** ✅

两个按钮 `:219` 「拍照」与 `:220` 「从相册选」；同一个弹窗也服务位置照片那一路（`WheremyRoot.kt:212` 的入口由 :329 的 FAB 与 :371 的位置页共用）。

**FR-SRC-04 换一张照片而不丢已填字段** ✅
录入页上 `ReviewScreen.kt:162` 「换一张」（已经有行的物品）或「选择照片」（还没有）；物品 id 与已填字段都不动，只换那两张图。

**FR-SRC-05 没相机的机器仍然能用** ✅

**FR-SRC-06 一张照片录多件物品** ✅
一次拍摄里如果有并排的几件东西，模型最多列 4 件（`Prompt.kt:19`），每件一个槽位；顶部芯片行切换，

"承托面不算一件"（桌子/柜子不是物品）写在提示词里（`Prompt.kt:20`）。
判据见 `RULES.md` §5.6 与 §5.7，落库时机见 `docs/superpowers/specs/2026-10-04-wheremy-multi-item-capture-design.md` §3。

**FR-SRC-07 「不要这件」** ✅

如果它已经有行（说明保存过），走删除，此时要有确认——按钮在 `ReviewScreen.kt:138`，判定见 `RULES.md` §6.5。

**FR-SRC-08 同一件物品的多角度（一张照片一件事、多张照片）** ✅ **已落地**（2026-10-13 用户拍板「完整做」，`ADR-26`）：一件物品可挂多张（上限 9）、封面恒为第一张、可加可删；`ItemPhotoMultiTest` 7 例 + `DetailScreenPhotoTest` 5 例 + 备份多图往返 1 例守着，G2 六处变异 6/6 都红。**本实现超出参照实现**（参照只做一件一张）

**2026-10-13 已写提案等用户拍板：`proposals/FR-SRC-08-多图.md`**——实测底子比原先估计的厚（表本来就是多行、详情页已在渲染列表、备份已按路径去重），真正要写的是「加/删照片」那条竖切，加上修两处只看封面那一张的引用计数（`ItemRepository.kt:485`、`:504`）；代价从「大」下修为「中」。

**FR-SRC-09 无照片的手填条目** ✅（不拍照，手动填）

### 3.2 AI 识别（FR-AI）

**FR-AI-01 照片 → 结构化字段预填** ✅
产出：`name / category / seasons / color / brand / material / aliases / description / tags / containerGuess`
（`data/vision/AnalysisResult.kt:3`）。**不产出数量与到期日**——那两个只能用户手填（`Daos.kt:64` 的注释钉住了这条）。

**FR-AI-02 AI 不阻塞手填，回来后不覆盖用户改过的字段** ✅
`ReviewScreen.kt:414` 「AI 正在看照片，可以先自己填」；合并规则（谁赢、逐字段）见 `RULES.md` §5，实现在 `ReviewViewModel.kt` `merge`（:229-249）。

**FR-AI-03 位置建议只认已有节点** ✅
模型只给通用容器词；本地 `SuggestLocationUseCase` 拿它去树里模糊匹配（整条路径相等 → 类型/名字匹配 → 平分取浅），
**匹配不到就留空，进待归类；绝不虚构不存在的位置**。用户已经选了位置时不覆盖（`CaptureFlow.kt` `suggest(...).takeIf { draft.locationId == null }`）。

**FR-AI-04 提示词带上用户已有的位置清单** ✅
本地有位置时，容器那一行从通用词表**替换**成用户的路径候选（不是追加），
这样模型才会回"主卧 / 衣柜"而不是永远回"橱柜"——见 `data/vision/Prompt.kt` 两版 `GUESS_*` 与 2026-10-04 马克杯实测。

**FR-AI-05 手动重新分析** ✅
录入页有「重新分析」。冷启动后重跑只能用 1600 原图（分析用的 1024 不落盘），多花一点 token，行为仍正确。
实现：`CaptureFlow.kt` `reanalyze` → `ItemRepository.photoBytesOf:204`。

**FR-AI-06 AI 失败永远降级，不阻塞录入** ✅
`AnalysisOutcome.Failed(reason)` → 字段留空 + 一句可读文案；原因分 11 类
（`NO_CONFIG / OFFLINE / TIMEOUT / UNAUTHORIZED / RATE_LIMITED / SERVER / BAD_RESPONSE / BAD_REQUEST / INSUFFICIENT_BALANCE / TRUNCATED / NOTHING_FOUND`），
文案见 `ui/common/UiFormat.kt` `failureText`。判据见 `RULES.md` §13。

**FR-AI-07 未配置 key 时静默跳过** ✅
`SettingsRepository.currentConfig()` 不可用 → 分析器直接给 `NO_CONFIG`，运行时不在两个实现间切换
（`di/AppContainer.kt:76` 的注释）。`OfflinePhotoAnalyzer` 留给单测与调试构建。

**FR-AI-08 换厂商只改 base_url + model** ✅
走 OpenAI 兼容 `POST {base_url}/chat/completions`，`temperature 0.1`、`max_tokens 2000`、
`response_format {"type":"json_object"}`。`max_tokens` 从 600 抬到 2000 是实测：推理模型的思考 token 会把答案截掉。

**FR-AI-09 AI 预填数量与到期日** ⬜
理由：食品保质期、保修卡的日期其实写在包装上，模型看得见。
触发条件：用户录一批食品/药品后抱怨每次都要手打日期。
代价：`AnalysisResult` 加字段 + 提示词加要求 + 合并规则要处理"日期字符串怎么解析、解析失败算不算 AI 给的"。
**注意**：加了这个字段，`Daos.kt:64` 那条"DRAFT 也要提醒"的理由（AI 不产出 expiresAt）要在注释里重写。

**FR-AI-10 对已有物品重跑分析（批量刷新）** ⬜
现在只能从录入页对单件重跑；换了更强的模型后，旧条目刷不新。
触发条件：模型换代，或用户明确要求"把那批都重认一遍"。
代价：要给 CONFIRMED 物品一个"AI 覆盖已确认字段"的确认交互——这直接和 `applyAnalysis` 的
"已确认不再被迟到的 AI 改写"（`ItemRepository.kt:111`）相撞，必须新加一条"用户主动要求才覆盖"的规则。

**FR-AI-11 词表外的类别/季节：照单入库，且筛得到也搜得到** ✅
提示词只给了 12 个类别（`Prompt.kt:25`）和四季（`:26`），而解析器不做白名单校验——
`AnalysisParser.kt:48` 的 `category` 与 `:49` 的 `seasons` 收的是任何字符串。模型回了词表外的值时：
- 详情页**看得见**：`DetailScreen.kt:213`、`:214` 直接打原值；
- 照片墙**筛不到**：芯片只遍历 `CATEGORIES`（`GalleryScreen.kt:211`）和 `SEASONS`（`:243`），
  而筛选是字符串相等比较（`ItemRepository.kt:330-331`），没有那颗芯片就没法按它筛；
- 搜索**也搜不到**：`search_text` 的组成里没有类别也没有季节（`ItemRepository.kt:324-327`）。
结果是"记是记下了，只能靠名字找到"。目标态二选一：把 AI 返回值夹回词表（并在界面上说一句"AI 说的类别不在清单里，
已按 其他 记"），或者让芯片行跟着库里真出现过的值长。完整链路见 `RULES.md` §5.7；把词表本身做成可编辑是 FR-CFG-06 ⬜。

**FR-REV-02 字段次序（表单信息架构）** ✅

**FR-REV-03 「保存」= 转 CONFIRMED + 名字必填** ✅

- 两个文件本身解不开 → "备份的 manifest.json 读不出来"（`:138`）与

**FR-BAK-06 引用完整性：四条拒，一条放行** ✅

## 4. 非功能需求

**NFR-01 性能**
- 落库在选图瞬间；照片解码/缩放/压缩都在 IO 线程（`CaptureFlow.kt:43` 的注释：几百毫秒就够看到卡顿）。
- 建树一次性全量入内存（位置几十到几百个），不用递归 SQL（否决项 D2）。
- 搜索 = 单列 `LIKE` + 内存排序，几千条量级几十毫秒。

**NFR-02 可靠性 / 不骗人**
这是这个项目最高的一条纪律：**界面上每一句话都必须真的成立**。
历史上有五句"说了没做"或"做了没说实话"被逐个改掉：待归类语义、退出弹窗对 CONFIRMED 说话、

## 6. 明确否决（⛔）与理由

留着这些是为了避免下一次又讨论一遍。**要推翻任何一条，得先在本文里改掉并写明新理由。**

| id | 否决的事 | 理由 |
|---|---|---|
| D1 | 语义向量搜索 / FTS5 / 以图搜图 | FTS5 默认 `unicode61` 把连续中文当一个 token，中文失效；要做对得自建 bigram 列，而个人量级 `LIKE` 几十毫秒够用。改动封在 `ItemDao` 一个方法里，将来要换也不亏 |
| D2 | 递归 SQL 建位置树 | 位置几百个，一次全量查出内存建树更简单，且规避各版本 SQLite 对 recursive CTE 支持差异 |
| D3 | 待归类独立表 | 它就是 `locationId IS NULL OR status='DRAFT'` 这个谓词；独立表会和真实位置状态打架 |
| D4 | 主题/动态取色设置项 | 单用户工具类 APP，动态取色会让**缩略图的色彩判断**失真（本产品靠颜色筛东西） |
| D5 | Hilt / DI 框架 | 一个普通 class 就装配完了，框架的收益不抵其复杂度（`di/AppContainer.kt`） |
| D6 | 回收站 / 软删除 | 删除用二次确认兜住；单人自用，"删错了"的成本低于维护软删除的复杂度 |
| D7 | Espresso / androidTest | 界面断言用 Robolectric + Compose 测试跑在 JVM，一条命令、无设备、CI 友好；只有相机这类 JVM 打不开的下真机 |
| D8 | 账号体系 / 云同步 / 多人共享 | 使用者一个人、一台机 |
| D9 | iOS / Web / **微信小程序** | 小程序每用户本地文件 200MB 配额（照片墙几百张就爆）；到期提醒靠"订阅消息"一次性授权不可靠；个人主体要类目审核 + AI 内容合规；"零安装"换不回这些约束 |
| D10 | 端侧大模型 | 手机本地模型认不出这些字段，且包体与功耗不可接受 |
| D11 | 商品条码扫码 / 电商价格 / 库存进出流水 | 这是"我记得东西在哪"的工具，不是进销存 |
| D12 | 备份里带设置或 key | 见 NFR-03，明文 key 跟着 zip 出门是不可接受的风险；设置项本身跨机重填一次很便宜 |
| D13 | 一张照片里"同一件的多角度"当多件处理 | 会让"最多 4 件"的额度被同一件吃掉；多角度属于 FR-SRC-08 |
| D14 | 「不要这件」加二次确认 | 它从不进库，点错重跑一次分析就行——加了确认反而拖慢主场景（用户拍板） |
