# 一张照片录多件物品 设计文档（主 spec §6.1 的增补）

日期：2026-10-04 主 spec：`2026-10-02-wheremy-design.md` §6.1 / §7 批次号：AJ 状态：用户已拍板（方案 2、一次最多 4 件、「不要这件」不做二次确认）

## 0. 要解决的问题

收纳场景里"一格一抽屉"常常一次拍下来就有好几样东西。现在的链路是**一张照片 = 一件物品**，
提示词第 19 行甚至明写着"识别其中**最主要的单个物品**。只输出一个 JSON 对象"，
所以一柜东西拍一张，用户只能自己一件一件重录。

## 1. 已确认的需求（来自用户原话）

- 走**方案 2**：确认页顶部能切到每一件，每件都能当场改字段再保存。
- 「AI 分析出多件物品时，我可能只想保存其中的一件，那其他的应该**容易操作取消保存或忽视掉**。」
- 一次最多 **4 件**。
- 「不要这件」**不做二次确认**（它从不进库，点错了重跑一次分析即可）。
- 探针照片：他相册里那张**骨传导耳机 + 手机支架**同框的图。

## 2. 非目标（明确不做）

- 不做"一张照片里同一件物品的多角度"（那是多张照片的事）。
- 不做模型识别结果的置信度排序 UI：超过 4 件时按模型返回顺序取前 4，界面上说"只列出前 4 件"。
- 不为多件引入新表、新列（见 §5 schema 承诺）。
- 不动 Plan 2 的 CameraX 取景：入口仍是系统相册选图。

## 3. 落库时机（这条决定其余一切）

| 时机 | 第 1 件 | 第 2..N 件 |
| --- | --- | --- |
| 选完照片的瞬间 | 落库（沿用主 spec §6.1"先落库再分析"） | 尚不存在 |
| AI 回来说有 N 件 | 字段写进行（`applyAnalysis`，仅 DRAFT） | **只活在内存**（`CaptureBatch` 里的草稿） |
| 点「保存这一件」 | 与今天相同 | 此刻才落库 |
| 点「不要这件」 | — | 从芯片上消失，库里从来没有过它 |
| 「稍后处理」 | 当前这件退回 DRAFT 进待归类 | 不受影响，仍在芯片上 |

**为什么其余件不"先全部落库再删"**：那会把批次 X 修过的"幽灵记录"重新请回来，而且用户说的
"忽视掉"就变成了"去待归类里逐件删"。

**代价（明说）**：AI 回来后不点保存就杀进程，那几件消失。它们本来也没被保存过，
与"忽视了掉"是同一件事。为防止误丢，退出确认跨件（§4）。

## 4. 确认页

- 顶部一排**横向可滑动的芯片**，一颗一件，标签是 AI 给的物品名；**未保存的那颗带一个圆点标记**。
- 切芯片 = 换整张表单；其余布局与今天一致。
- **只识别出 1 件时那排芯片压根不出现**，界面与今天逐像素相同（这是回归锚）。
- 实现落在这里时改了主意：**一个 `ReviewViewModel` 持有 N 个 `ReviewSlot`**，而不是原写的
  "一件一个 VM 实例"。原因是三件事都要求有一处同时握着整批——每件各算一次位置建议（§6）、
  退出时按"还有 K 件没保存"点名（下面那条）、以及「换一张」= 整批重跑（再下面那条）。
  一件一个 VM 的话，这三处都要变成外壳（`WheremyRoot`）里的跨 VM 协调，而外壳本来只管"开哪一页"。
  草稿、`touched`、`saved` 逐件独立存在槽位里，所以批次 X/Z 的既有语义是一条条搬进槽位，没有重写。
- 退出（✕ 与系统返回）：任一件有未保存内容就弹**一次**确认，文案点名"还有 K 件没保存，
  离开后它们不会留下"；`touched` 全空时仍按批次 Z 直接关页。
- 「换一张」= **整批重跑**：换掉的那张图才是这几件的来源，旧结果没有意义。
  其余件丢弃并提示一句，第 1 件仍留在库里（itemId 不变，走 `swapPhoto`）。

## 5. 共享一张照片的三条硬前提

两件物品共用同一对文件（原图 + 缩略图），必须先解决这三条，否则会出现"删掉一件把另一件的图删了"。

1. **删文件要引用计数**。`ItemRepository.delete`（246 行）与 `swapPhoto`（86 行）现在是无条件
   按照片行删文件。改法：删之前先查"还有别的 `item_photo` 行指着这个路径吗"，有则只删行不删文件。
2. **备份导出按路径去重**。`BackupRepository.export`（60 行）逐行 `putFile(row.filePath)`，
   两行同路径会往 zip 里塞两个同名条目。导入侧按路径落盘，所以只需导出去重；
   `summary.photos` 的含义改为"写出的**不同文件对**数"。
3. **新增仓库方法** `newDraftSharingPhoto(sourceItemId)`：写一行新物品 + 一条指向同一对路径的
   `item_photo` 行，两条写同一个事务（与 `newDraft` 同样的"行成了文件才有主"约束）。

**schema 承诺**：以上只新增 Dao 查询与仓库方法，`@Entity` 字段一字不改，
`DB_SCHEMA_VERSION` 保持 1，验收期的 schema 冻结不破，`install -r` 不丢用户数据。

## 6. AI 契约

- 提示词：从"识别最主要的单个物品，只输出一个 JSON 对象"改为
  "识别照片里最多 4 件物品，输出 `items` 数组，每件字段与现在相同"。
  位置候选那段（批次 AH 的 `systemFor`）继续跟着，`container_guess` 变成**每件各一个**。
- **解析器必须同时认两种形状**：`{"items":[...]}` 数组，以及现在这种单个对象。
  只改提示词不改解析器会静默退化成"只录一件"——`AnalysisParser.extractObject` 现在是
  "取第一个带我们认识的字段的结果"（45 行），模型回数组时它只会留下第一件，
  看起来像模型没认出来。这是本设计里最容易做漏且最容易假装成功的一处。
- `finish_reason = length` 仍按批次 U 分类为"被截断"，不许冒充"无法解析"。
  多件的 JSON 更长，而 `deepseek-flash` 的 reasoning token 也计入 `max_tokens = 2000`，
  所以探针必须专门看这一项。
- **`PhotoAnalyzer` 返回类型改为多件**（`List<AnalysisResult>` + failure），
  `applyAnalysis` 仍只对第 1 件（已落库那件）写字段，其余件的字段留在内存草稿里。
  位置建议（`SuggestLocationUseCase`）**每件各算一次**，用的是同一批候选路径与同一棵树——
  批次 AH 那条"喂给模型的路径和回来匹配的路径必须是同一批"在每件上都成立。

### 7.1 探针实测结论（2026-10-04 17:32，9aa4b43e，切片 1 的包）

用的就是他指定的那张 13:16 实拍（骨传导耳机 + 蓝色手机支架，灰色桌垫上，边上还有黑色托盘）。
模型原文回话：`{"items":[ … ]}` **三件**，`finish_reason=stop`。

1. **形状与件数**：确实是 `{"items":[…]}`，三件按"前景 → 背景"排。切片 1 的解析器读到的第一件
   正常落进确认页（名称「骨传导耳机」＋「AI 猜的位置：家 / 抽屉（已填进「放在哪里」）」）。
2. **每件字段**：十个字段每件都给全（没有的显式给 `null`、`seasons` 给 `[]`）。
   `container_guess` 每件各算一个：耳机和"笔记本"都给了 `家 / 抽屉`（他树里真有的路径），
   桌垫给 `null`。**批次 AH 那条"只能从清单里原样选"的约束在多件下没被冲掉。**
3. **截断**：三件原文约 700 字符，`max_tokens=2000` 没碰边。→ **上限保持 4、`max_tokens` 保持 2000**；
   真被切断时批次 U 的 `TRUNCATED` 会如实说"答案太长被切断"，不会冒充"无法解析"。
4. **第 2 件的缩略图**：探针阶段没有界面可验，**推到切片 4**（届时用同一张图走两件保存）。

两条探针带出来的新事实：

- **模型会把承托面当成一件**（这次多报了一件"桌垫"）。这不改设计，反而印证了 §4 的
  「不要这件」必须一步点掉、且不需要二次确认——每件垃圾都要多点一下的界面没人用。
  是否加一句"不要把桌面、地板、床这类承托面当成物品"另说：**改了提示词就得再真机验一次**，
  留到切片 2 一并跑，不在本地测试里假装验过。（已跑完，见 §7.2。）
- **支架被认成"蓝色笔记本"**：这是视觉准确度，不在本批范围，本批只保证"认成什么都录得下来、
  改得掉、丢得掉"。

探针用的临时日志已删除，装回设备的包与 `HEAD` 一致；探针当场创建的 DRAFT 已删，
他 13:16 自己录的那条「骨传导耳机」（CONFIRMED）原样保留。

## 8. 测试策略

本地（Robolectric + MockWebServer）：

- 解析器：数组两形、单对象仍可用、数组里混入不认识字段的那件被跳过而不是整批失败、被截断仍报截断。
- 落库时机：丢弃的其余件在库里查不到行、也不留文件；「保存这一件」才出现第 2 条 item 行。
- 引用计数：两件共用一张图，删掉第 1 件后第 2 件的原图与缩略图文件仍在、仍能显示。
- 备份：导出去重后 zip 里只有一个同名条目；覆盖导入往返后两件各自指回同一对文件。
- 界面：芯片排只在 >1 件时出现；切芯片不丢已填字段；跨件退出确认点名件数；「不要这件」后芯片消失。
- 变异验证：至少对"解析器只认单对象"和"删文件不查引用"两处做，确认新用例有牙。

### 8.1 实测记录（切片 4b，2026-10-04 晚）

三次变异，每次只改一行生产代码，跑确认页两个测试类（60 例）：

| 变异 | 变红的用例 |
|---|---|
| `updateCurrent` 写死槽位 0（手打内容不分件） | 3 条 VM + 1 条 UI |

写错槽位在这条路径上看不出来——断言里写着"要落到这一件的草稿上"，实际只验证了"落到第 1 件的草稿上"。

## 9. 验收标准（用户视角）

1. 一张里有两样东西的照片进去，能在确认页顶部看到两颗芯片，各自能改名、选位置、保存。
2. 只想要其中一件时，另一件点「不要这件」就没了，待归类里不会冒出多余条目。
3. 保存下来的两件在照片墙上各自有缩略图，删掉其中一件，另一件的图不丢；
   而且删之前问的那句话说的是这件事（不会承诺"照片会一起删除"）。
4. 只有一件物品的老照片，界面与今天没有区别。

## 10. 一处待拍板 → 已拍板：删除确认框按共用情况说话（批次 AK）

详情页那颗「删除」的确认框原来写死**「照片和记录会一起删除，无法恢复。」**——批次 AJ 之后这句
不再总是为真：两件共用一张图时，删掉其中一件只删行，文件留给另一件。

用户 2026-10-04 拍板：算"说法不诚实"，要改，并且**分类要整理好、实际处理也要分类执行**。
实际处理经查已经是对的（`deleteUnreferenced` 按 `refsTo(path) == 0` 才回收文件，原图与缩略图两列
一起数），欠的只有文案，所以本批只补"说准这句话"所需的数据与分档，不改删除行为。

三档分类落在数据层（`ItemRepository.photoDeletionOf` 返回 `PhotoDeletion(hasPhoto, otherItems,
otherOwners)`），措辞落在 `ui/common.deleteWarningOf`，详情与照片墙两个入口共用同一函数：

| 情况 | 那句 |
|---|---|
| 这件根本没照片 | 这条记录会被删除，无法恢复。 |
| 还有 N 件物品在用 | 这张照片还有 N 件物品在用，删掉这一件只会去掉这一件的记录，照片留着。 |
| 只有非物品的主人（位置记录）在用 | 这张照片还有别的记录在用，删掉这一件只会去掉这一件的记录，照片留着。 |
| 只这一件在用 | 照片和记录会一起删除，无法恢复。 |

第三档正常操作造不出来（要给抽屉拍的位置记录也能手改备份包塞进同一对文件），但"照片会一起没"
在那种情况下同样是假话，所以数 `ownerType` 时把非 `item` 的主人单列出来，而不是当成 0。

那句话在按下「删除」的那一刻现查，随 id 一起存成 `PendingDelete`：加载期不多算一次读，
未加载时也不会凭默认值写出一句可能不真的话。
